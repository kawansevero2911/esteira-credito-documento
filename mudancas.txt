======================================================================
1. CONTEXTO DO PROJETO
======================================================================

O projeto está inserido na Esteira de Crédito da disciplina de Análise e
Projeto de Sistemas I. O grupo é responsável pela camada de estruturação e
emissão de documentos da operação de crédito.

Na primeira entrega, a responsabilidade definida para o grupo foi receber
uma operação em JSON, validar sua estrutura, mapear os dados para um modelo
documental, gerar um documento em PDF, armazenar os metadados do documento em
um repositório orientado a documentos e publicar uma referência do documento
gerado.

O processo foi modelado em BPMN com o seguinte fluxo:

recebimento dos dados -> validação -> decisão "Dados válidos?" ->
mapear dados -> gerar PDF -> armazenar -> publicar evento -> documento
disponibilizado.

======================================================================
2. COMO O PROJETO ESTAVA ANTES
======================================================================

Antes desta evolução, o grupo possuía um protótipo local desenvolvido em
Python.

O protótipo era executado diretamente pelo arquivo principal e carregava um
JSON de exemplo. A execução realizava as etapas do processo documental de
forma local.

A estrutura original possuía módulos separados para:

- validação da operação;
- mapeamento dos dados;
- geração do PDF;
- armazenamento dos metadados;
- publicação simulada do evento;
- orquestração do fluxo.

Também existiam:

- um JSON Schema para a operação de crédito;
- um exemplo de operação;
- diretórios para armazenamento dos PDFs e metadados.

O armazenamento era simulado por arquivos JSON em disco, representando um
repositório orientado a documentos.

A publicação do evento também era simulada: o protótipo imprimia no terminal
uma estrutura de evento com a referência do documento gerado.

A validação original utilizava uma implementação simplificada de um subconjunto
de JSON Schema, evitando dependência de uma biblioteca externa.

======================================================================
3. LIMITAÇÕES IDENTIFICADAS NO PROTÓTIPO
======================================================================

As principais limitações identificadas foram:

1. A funcionalidade não estava exposta como uma API REST.
2. O fluxo dependia da execução direta do programa principal.
3. A entrada era baseada em um arquivo JSON de exemplo, e não em uma
   interface de comunicação entre módulos.
4. A validação era uma implementação simplificada de JSON Schema.
5. O armazenamento ainda era feito em arquivos locais.
6. A publicação do evento era apenas uma simulação por saída no terminal.
7. O contrato da operação ainda precisava ser preparado para integração com
   os demais módulos da Esteira.
8. Não havia uma interface HTTP documentável para consumo pelos outros grupos.

======================================================================
4. ALTERAÇÕES REALIZADAS
======================================================================

4.1. TRANSFORMAÇÃO DO PROTÓTIPO EM API REST

Foi criada uma API REST utilizando FastAPI.

Endpoint criado:

POST /api/documentos

Responsabilidade:
- receber os dados da operação em JSON;
- iniciar o processo de validação;
- executar o fluxo documental;
- retornar o identificador do documento e a referência do evento gerado.

Também foi criado:

GET /api/documentos/{documento_id}

Responsabilidade:
- consultar os metadados de um documento previamente gerado.

Foi criado ainda:

GET /api/saude

Responsabilidade:
- permitir uma verificação simples da disponibilidade do serviço.

4.2. VALIDAÇÃO POR JSON SCHEMA

A validação simplificada existente foi substituída pela utilização da
biblioteca jsonschema com o Draft 2020-12.

A API valida os dados antes de executar o mapeamento, a geração do PDF, o
armazenamento e a publicação do evento.

Quando os dados não atendem ao contrato, a API retorna erro de validação e o
fluxo documental não continua.

4.3. ORGANIZAÇÃO DO FLUXO DE NEGÓCIO

A lógica principal foi retirada do arquivo de execução direta e organizada no
módulo processo.py.

Isso separa a camada HTTP da lógica do processo e mantém as responsabilidades
identificadas na primeira entrega.

4.4. GERAÇÃO DO DOCUMENTO

A geração do PDF foi mantida como uma responsabilidade independente, usando
o módulo gerador_pdf.py.

O mapeador prepara os dados para o documento e o gerador cria o arquivo PDF.

4.5. ARMAZENAMENTO

Foi mantida a estratégia de armazenamento local orientado a documentos como
solução desta etapa.

Os metadados são armazenados em JSON e recebem um identificador único.

A interface RepositorioDocumentos foi preservada para facilitar uma futura
substituição por uma base de documentos, como MongoDB ou outra solução que
venha a ser definida pelo grupo.

4.6. PUBLICAÇÃO DO EVENTO

A publicação do evento continua sendo uma simulação, mas deixou de depender
apenas de um print no terminal.

O evento estruturado também é registrado em arquivo JSON, permitindo que o
formato da mensagem seja testado e posteriormente substituído por uma
integração com um barramento real.

O evento contém, entre outras informações:
- evento;
- id_operacao;
- documento_id;
- caminho_pdf;
- data/hora de publicação.

4.7. DOCUMENTAÇÃO AUTOMÁTICA DA API

A API foi construída com FastAPI, que disponibiliza uma especificação
OpenAPI e uma interface Swagger UI automaticamente.

A documentação pode ser acessada em /docs quando a aplicação estiver em
execução.

A revisão e o refinamento dos contratos, exemplos e descrições dos endpoints
continuam como atividade de documentação do projeto.

4.8. TESTES

Foram preparados testes automatizados para:

- verificar a disponibilidade da API;
- verificar o fluxo de criação de um documento com operação válida;
- verificar a rejeição de uma operação inválida.

Os testes verificam tanto o caminho de sucesso quanto o caminho de erro,
coerentes com o gateway "Dados válidos?" do processo BPMN.

======================================================================
5. POR QUE AS ALTERAÇÕES FORAM FEITAS
======================================================================

A principal motivação foi aproximar o protótipo da arquitetura necessária
para a Esteira de Crédito.

O protótipo original demonstrava a mecânica interna do processo, mas os
outros módulos da Esteira precisam de uma interface de comunicação para
consumir a funcionalidade do grupo.

A criação da API REST permite que a funcionalidade seja acionada por outros
módulos sem depender da execução manual de um arquivo Python.

A adoção de JSON Schema como contrato formal reduz o risco de que dados em
formato inesperado avancem para as etapas de geração e armazenamento do
documento.

A separação entre API, validação, mapeamento, geração, armazenamento e evento
mantém as responsabilidades desacopladas e favorece a evolução da solução.

6. INTEGRAÇÃO COM OS OUTROS GRUPOS

outros módulos da Esteira, incluindo Score, Decisão, Cálculo de Juros e

Essas informações foram utilizadas como referência para a evolução da
arquitetura, mas esta entrega não declara como implementada uma integração
externa que ainda não possui endpoint definitivo disponibilizado pelo grupo

A API deste grupo está preparada para receber um contrato JSON e executar o
processo documental. A composição final dos dados recebidos de Score,

intergrupos forem oficialmente consolidados.

13. ATUALIZAÇÃO v1.1.0 - SWAGGER CONFIGURADO PARA DOCUMENTAÇÃO DOS
    ENDPOINTS
======================================================================

13.1. COMO ESTAVA

Na v1.0.0 a API já exibia o Swagger em /docs, mas apenas com o que o FastAPI
gera sozinho. Na prática:

- os endpoints apareciam só com o nome da função (ex.: "Criar Documento"),
  sem resumo nem explicação do que fazem;
- o corpo do POST /api/documentos aparecia como um objeto genérico
  ("additionalProperties: true"), sem nenhum campo. Quem abria o Swagger não
  sabia quais campos enviar, quais eram obrigatórios nem os tipos de produto
  aceitos;
- não havia exemplo de requisição: para testar era preciso copiar o JSON de
  examples/ manualmente;
- as respostas não tinham modelo definido: o 201 aparecia sem campos e
  o Swagger não mostrava as respostas 400 (DADOS_INVALIDOS) e 404 (documento não
  encontrado);
- as tags "Infraestrutura" e "Documentos" existiam, mas sem descrição;
- a própria mudancas.txt (item 4.7) e o README registravam o refinamento do
  Swagger como atividade pendente;
- os testes cobriam só 3 cenários (saúde, criação válida e inválida) e não
  verificavam a documentação.

13.2. MUDANÇAS REALIZADAS

a) src/api.py - configuração do Swagger
   - Descrição geral da API em Markdown: responsabilidade do grupo, fluxo
     BPMN resumido e um passo a passo de como testar pelo "Try it out".
   - Descrição das tags "Infraestrutura" e "Documentos".
   - summary e description em todos os endpoints.
   - Versão da API alterada de 1.0.0 para 1.1.0.
   - Parâmetros do Swagger UI: endpoints listados recolhidos, modelos
     visíveis e tempo de resposta exibido em cada chamada.
   - Rota "/" redireciona para "/docs" (não aparece na documentação).

b) Contrato de entrada documentado com o próprio JSON Schema
   - O Swagger passou a usar o arquivo schemas/operacao_credito.schema.json
     como o schema "OperacaoCredito" do corpo do POST /api/documentos.
   - Foram removidos apenas os campos $schema e $id, que não se aplicam
     dentro do OpenAPI. O OpenAPI 3.1 usa o mesmo JSON Schema 2020-12 que a
     validação já usa, então não foi preciso reescrever o contrato.

c) Exemplos de requisição
   - Os arquivos examples/operacao_valida.json e
     examples/operacao_invalida.json aparecem como exemplos selecionáveis no
     "Try it out", cada um com o resultado esperado (201 ou 400).

d) src/modelos.py (novo) - modelos de resposta
   - Saude, DocumentoCriado (com DocumentoResumo e EventoDocumentoGerado),
     DocumentoMetadados, ErroDadosInvalidos e ErroNaoEncontrado.
   - Cada campo tem descrição e exemplo.
   - Os endpoints declaram as respostas 201/400 (POST) e 200/404 (GET), e
     o FastAPI mantém a 422 para corpo que não é um objeto JSON.

e) Parâmetro documento_id
   - Recebeu descrição (de onde vem o valor) e exemplo.

f) scripts/exportar_openapi.py (novo)
   - Gera docs/openapi.json sem subir o servidor, com o comando
     "python -m scripts.exportar_openapi". O arquivo pode ser enviado aos
     outros grupos ou aberto em https://editor.swagger.io.

g) Testes (tests/test_api.py) - de 3 para 11 testes
   - Novos testes de endpoint: consultar um documento criado e consultar
     um documento inexistente (404); o teste inválido agora confirma que
     nenhum PDF foi gerado.
   - Novos testes de documentação: /docs, /redoc e o redirecionamento de
     "/" respondem; todos os endpoints têm summary, description e tag; o
     corpo do POST referencia o schema OperacaoCredito, que é igual ao
     arquivo do contrato; os exemplos estão presentes; as respostas de erro
     400 e 404 estão documentadas.
   - pytest.ini (novo) permite rodar os testes apenas com "pytest".

h) README.md
   - Tabela de endpoints com os códigos de resposta.
   - Nova seção "Documentação Swagger / OpenAPI" com os endereços /docs,
     /redoc e /openapi.json, o que está documentado e como exportar.

O QUE NÃO MUDOU
- A lógica do processo (validar, mapear, gerar PDF, armazenar, publicar) é
  a mesma da v1.0.0.
- A validação da entrada continua sendo feita pelo JSON Schema via
  jsonschema, com o mesmo erro 400 DADOS_INVALIDOS. Os modelos Pydantic
  foram usados apenas nas respostas.
- O contrato de entrada e os formatos de resposta não mudaram. Os
  consumidores atuais não são afetados.

13.3. POR QUE AS MUDANÇAS FORAM FEITAS

- Integração com os outros grupos: Score, Decisão, Cálculo de Juros e
  Financiamento de Automóveis precisam saber exatamente o que enviar e o
  que recebem. Com o Swagger documentado, o contrato fica disponível em um
  endereço da própria API, sem depender de conversas ou arquivos soltos.
- Uma fonte única para o contrato: se o Swagger tivesse um modelo próprio,
  escrito à parte, ele poderia ficar diferente do JSON Schema que a API
  realmente usa para validar. Reaproveitar o arquivo do schema garante que
  a documentação mostra exatamente o que é validado.
- Manter o erro 400 DADOS_INVALIDOS: se a entrada fosse validada por um
  modelo Pydantic, o FastAPI passaria a responder 422 com outro formato de
  erro, quebrando o comportamento combinado e o gateway "Dados válidos?"
  do BPMN. Por isso o Pydantic ficou restrito às respostas.
- Testar pela própria documentação: os exemplos prontos permitem que o
  professor e os outros grupos executem o fluxo válido e o inválido
  direto pelo navegador.
- Documentar os erros: quem integra precisa tratar o 400 e o 404, então
  esses retornos também precisam estar descritos.
- Evitar que a documentação fique desatualizada: os testes falham se
  um endpoint for criado sem descrição ou se o Swagger deixar de refletir
  o contrato.

14. ATUALIZAÇÃO v1.2.0 - CONTRATO JSON CANÔNICO DA ESTEIRA DE CRÉDITO
======================================================================

14.1. COMO ESTAVA

Até a v1.1.0 o contrato de entrada era plano, em snake_case, e servia
apenas para o protótipo deste grupo:

  {"id_operacao", "tipo_produto", "cliente": {"nome", "documento"},
   "valor", "prazo_meses", "taxa_juros_mensal"}

Limitações concretas:

- não havia onde colocar as informações dos outros nove processos da
  Esteira: score, decisão, juros, cronograma de parcelas, promoções,
  produto financeiro, dados de financiamento;
- o contrato só representava pessoa física, e de forma indireta: o campo
  "documento" era um texto livre que tanto podia ser CPF quanto CNPJ;
- não havia distinção entre o que é obrigatório sempre e o que é
  obrigatório apenas para determinado produto;
- o schema era um único arquivo, sem versionamento declarado;
- validavam-se tipos e faixas simples; não havia validação de CPF, de
  data real, de timestamp UTC, de casas decimais nem de enums dos outros
  grupos;
- o mapeador montava um dicionário fixo de 8 campos, e o PDF era
  desenhado linha a linha no canvas, com um layout só;
- o registro de metadados tinha 4 campos e o evento, 5;
- repositório e publicador eram classes concretas, sem interface;
- não havia exemplo de PJ, de score, de decisão nem de operação
  financeira.

14.2. O QUE MUDOU

a) CONTRATO CANÔNICO MODULAR (schemas/v1/)

   O contrato deixou de ser específico deste serviço e passou a ser o
   contrato canônico da Esteira: um contrato único, dividido em blocos,
   em que cada processo preenche apenas o que é da sua responsabilidade.

   Blocos e responsáveis:
     correlacao, metadados ....... comuns a todos os processos
     documento ................... Processo 6  (este grupo)
     cliente, cadastro, credito .. Processo 3  (Crédito PF e PJ)
     promocao .................... Processo 1  (Promoções)
     produtoFinanceiro ........... Processo 7  (Produtos Financeiros)
     financiamento ............... Processos 4 (Imóveis) e 8 (Automotivo)
     score ....................... Processo 10 (Score)
     juros ....................... Processo 5  (Cálculo de Juros)
     decisao ..................... Processo 9  (Decisão)
     operacaoFinanceira .......... Processo 2  (Controle Financeiro)

   Arquivos novos em schemas/v1/: operacao_credito, comuns, correlacao,
   documento, cliente, cadastro, promocao, credito, produto_financeiro,
   financiamento, score, juros, decisao, operacao_financeira, metadados.

   CONSOLIDAÇÃO DOCUMENTADA: o roteiro previa os blocos
   "operacaoFinanceira" e "controleFinanceiro" separados. Os dois
   descreviam a mesma operação e o mesmo cronograma, produzidos pelo
   mesmo processo. Foram unificados em "operacaoFinanceira" para não
   duplicar informação.

b) OBRIGATORIEDADE EM TRÊS NÍVEIS

   Sempre: schemaVersion, correlacao.idOperacao, documento.tipoDocumento
   e cliente.tipoPessoa. Só isso.

   Por tipo de pessoa (if/then no schema):
     PF -> exige cliente.dadosPF com nomeCompleto e cpf
     PJ -> exige cliente.dadosPJ, SEM nenhum campo interno obrigatório

   Por produto (if/then no schema):
     IMOBILIARIO -> exige financiamento.imobiliario (valorImovel,
                    valorEntrada, prazoMeses, taxaJurosMensal,
                    sistemaAmortizacao), cadastro.rendaMensal,
                    cliente.endereco (logradouro e cidade) e, para PF,
                    dataNascimento
     AUTOMOTIVO  -> exige apenas financiamento.automotivo, sem campos

   Operação automotiva não exige dados imobiliários, e vice-versa.

c) BLOCOS ABERTOS PARA CONTRATOS QUE AINDA NÃO EXISTEM

   promocao, credito, produtoFinanceiro, juros, decisao,
   financiamento.automotivo e cliente.dadosPJ usam
   additionalProperties: true e não exigem nada. A área arquitetural
   existe, nada é inventado, e a pendência fica escrita na própria
   description do schema. Os demais blocos são estritos
   (additionalProperties: false).

d) VALIDAÇÃO DE VERDADE (src/validador.py)

   Passou a validar: CPF com 11 dígitos, CNPJ com 14, datas que existem
   no calendário (2026-02-31 é recusada), timestamps ISO-8601 em UTC,
   score inteiro de 0 a 1000, numeroOperacao no padrão OP-AAAA-NNNNNN,
   casas decimais (2 para dinheiro, 6 para taxa) e todos os enums
   informados pelos grupos.

   Duas extensões foram necessárias:

   - verificação de "format": por especificação, format é só anotação e
     a maioria dos validadores não a confere. Foram registrados
     verificadores próprios para date, date-time, uuid e email, escritos
     só com a biblioteca padrão do Python - sem dependência nova.

   - palavra-chave "x-casasDecimais": o limite de casas decimais NÃO
     pode usar multipleOf, porque multipleOf opera em ponto flutuante e
     reprova valores válidos (1234.56 / 0.01 = 123455.99999999999). A
     comparação é feita em Decimal. Validadores de outras linguagens
     ignoram a extensão, e isso está documentado.

   O erro passou a vir também em forma estruturada, no campo "erros",
   com campo/mensagem/regra - mais simples de tratar em Java, Go ou
   JavaScript. O campo "detalhes" continua no formato de texto da
   v1.0.0.

e) CONTRATO MODULAR NA FONTE, CONSOLIDADO NA PUBLICAÇÃO
   (src/contrato.py, scripts/gerar_bundle_schema.py)

   A fonte da verdade são os arquivos de schemas/v1/. Para publicar,

f) COMPATIBILIDADE COM A v1.0.0 (src/compatibilidade.py) - ARQUIVO NOVO

   O formato plano antigo CONTINUA FUNCIONANDO. Mensagens antigas são
   convertidas para o contrato canônico e só então validadas: existe um
   único contrato e um único ponto de validação. A resposta informa o
   formato recebido em "formatoEntrada".

   A conversão remove pontuação do documento e usa a quantidade de
   dígitos para decidir PF (11) ou PJ (14). Ela NÃO preenche campo
   ausente: o que faltava continua faltando e a validação acusa.

g) MODELO DOCUMENTAL (src/modelo_documental.py) - ARQUIVO NOVO

   Estrutura intermediária imutável entre o contrato e o PDF, em seções,
   campos e tabelas. O PDF passou a ser gerado do modelo, e não do JSON
   bruto: o gerador não conhece mais o contrato de entrada.

h) MAPEADOR (src/mapeador.py) - REESCRITO

   De 8 campos fixos para seções por área: CLIENTE, PRODUTO, IMÓVEL,
   FINANCEIRO (perfil e condições), ANÁLISE, DECISÃO, OPERAÇÃO,
   PARCELAS e METADADOS. Uma seção só aparece se o bloco correspondente
   veio.

   O que NÃO veio por depender de outro processo é listado no rodapé do
   PDF, em "INFORMAÇÕES NÃO RECEBIDAS" - em vez de sumir em silêncio.

   O mapeador formata; não calcula. Não recalcula score, juros, decisão,
   risco, parcelas nem saldos, e não preenche campo ausente com valor
   padrão.

i) TEMPLATES DE PDF POR PRODUTO (src/templates_pdf/) - PASTA NOVA

   O template é escolhido por uma chave definida pelo mapeador,
   resolvida num registro - não por if espalhado pelo gerador.
   Implementados: proposta_credito (genérico) e proposta_imobiliaria
   (com painel de destaques).

   Crédito PJ e financiamento automotivo usam o genérico de propósito,
   porque seus dados ainda não foram definidos.

   A geração passou a usar o Platypus do ReportLab, em vez de desenho
   direto no canvas: um cronograma pode ter centenas de parcelas, e o
   Platypus quebra a tabela entre páginas e repete o cabeçalho sozinho.
   ReportLab continua sendo a biblioteca usada.

j) REPOSITÓRIO (src/repositorio.py) - INTERFACE + IMPLEMENTAÇÃO

   RepositorioDocumentos virou interface (ABC) e
   RepositorioArquivosJson é a implementação atual. Trocar por MongoDB é
   escrever uma classe nova. MongoDB NÃO é exigido nesta etapa.

   O registro passou de 4 para 12 campos: documento_id, _id (mantido da
   v1.0.0), id_operacao, criado_em, tipo_documento, tipo_produto,
   versao_schema, caminho_pdf, status, hash_documento (SHA-256 do PDF),
   template e correlacao.

   CORREÇÃO DE SEGURANÇA: a consulta por documento_id passava o valor da
   URL direto para o caminho do arquivo, então um id como
   "../../etc/passwd" leria fora da pasta de armazenamento. Agora o

k) EVENTOS (src/publicador_evento.py) - INTERFACE + FORMATO VERSIONADO

   Nenhum barramento real (Kafka, RabbitMQ) foi implementado, conforme

l) ORQUESTRAÇÃO (src/processo.py) - REESCRITO

m) SWAGGER (src/api.py)

- MongoDB e barramento real: fora do escopo desta etapa. Só as

15. CORREÇÃO - COERÊNCIA DO MODELO DE SCORE EM PESSOA JURÍDICA
======================================================================

15.1. O QUE ESTAVA ERRADO

O contrato 1.2.0 declara, na própria description da regra
RegraCoerenciaModeloScore, que o código do modelo de score precisa ser
coerente com o tipo de pessoa: SCORE_PF para pessoa física e SCORE_PJ
para pessoa jurídica.

O schema, porém, verificava apenas a metade de pessoa física. Uma
operação de pessoa jurídica acompanhada de um score calculado pelo
modelo SCORE_PF era ACEITA, contrariando o que o próprio contrato
dizia. O documento sairia apresentando um resultado produzido pelo
modelo errado, sem nenhum aviso.

15.2. O QUE MUDOU

Em schemas/v1/operacao_credito.schema.json, a regra foi dividida em
duas, seguindo o mesmo padrão que o arquivo já usava para os pares
RegraPessoaFisica / RegraPessoaJuridica e RegraFinanciamentoImobiliario
/ RegraFinanciamentoAutomotivo:

- RegraCoerenciaModeloScorePessoaFisica: tipoPessoa PF exige
  score.modelo.codigo igual a SCORE_PF (comportamento que já existia);
- RegraCoerenciaModeloScorePessoaJuridica: tipoPessoa PJ exige
  score.modelo.codigo igual a SCORE_PJ (metade que faltava).

As duas regras só valem quando o bloco score está presente. Uma
operação sem score continua válida, como antes.

Arquivos alterados:

- schemas/v1/operacao_credito.schema.json - regra dividida em duas;
- schemas/operacao_credito.schema.json - contrato consolidado regerado
  por python -m scripts.gerar_bundle_schema;
- tests/apoio.py - novo apoio operacao_minima_pj(), a menor operação
  válida de pessoa jurídica;
- tests/test_validacao.py - o teste
  test_modelo_do_score_precisa_combinar_com_o_tipo_de_pessoa, que
  cobria só PF, virou dois testes, um por tipo de pessoa, e cada um
  confere tanto o par correto (aceito) quanto o par trocado (recusado);
- docs/contrato-json.md - nova subseção "Coerência entre blocos", com as
  duas condições em tabela;
- docs/integracao.md - a frase que mencionava apenas SCORE_PF para PF
  passou a citar os dois casos.

15.3. POR QUE A VERSÃO DO CONTRATO CONTINUA 1.2.0

Nenhum campo foi criado e nenhuma regra de negócio foi inventada. Os
dois códigos de modelo (SCORE_PF, SCORE_PJ) e os dois tipos de pessoa
(PF, PJ) foram informados pelo grupo Score, e a regra já estava escrita
na description do contrato 1.2.0: o schema apenas não a aplicava por
inteiro.

Portanto isto não é uma mudança de contrato, e sim a aplicação do
contrato que já estava publicado. Subir para 1.3.0 sugeriria campo novo,
e subir para 2.0.0 sugeriria quebra de compatibilidade - nenhuma das
duas descreve o que aconteceu.

Registro honesto da consequência: uma mensagem de PJ com modelo
SCORE_PF, que antes era aceita, agora é recusada com erro em
score.modelo.codigo. Nenhum grupo é afetado, porque a versão 1.2.0 do
contrato ainda não havia sido publicada no repositório remoto quando a
correção foi feita.

16. BANCO DE PROVAS E SERVIDOR DE FUMAÇA
======================================================================

16.1. O PROBLEMA

Para conferir a API havia duas opções: o Swagger, que exige
pip install, e o curl, que exige montar o JSON na mão. Nenhuma das
duas serve para mostrar o projeto rodando numa máquina sem acesso à
rede, nem para quem quer apenas ver o contrato aceitando e recusando.

16.2. O QUE FOI CRIADO

web/index.html - banco de provas

Página única, sem build, sem framework e sem dependências. Cobre os
três endpoints: GET /api/saude, POST /api/documentos e
GET /api/documentos/{documento_id}.

A tela lista os sete casos de examples/, carrega o JSON escolhido num
campo editável e mostra o que o contrato respondeu:

- 201: identificador do documento, operação, produto, template do PDF,
  versão do contrato, caminho do arquivo, hash SHA-256 e o evento
  documento.gerado publicado;
- 400: o código DADOS_INVALIDOS e a lista de campos recusados, cada um
  com o caminho, a regra violada e a mensagem;
- 404 na consulta de um identificador que não existe;
- sem resposta: as instruções para subir o backend.

Os exemplos ficam EMBUTIDOS no arquivo, porque a página precisa
funcionar aberta direto do disco, e o protocolo file:// não lê arquivos
vizinhos.

web/modelo.html e scripts/gerar_frontend.py

Embutir cria o risco de a página envelhecer em relação a examples/. O
molde fica em web/modelo.html, com o marcador onde os exemplos entram,
e scripts/gerar_frontend.py copia os exemplos reais para dentro dele -
o mesmo arranjo que o contrato já usa entre schemas/v1/ e o arquivo
consolidado.

scripts/servidor_local.py

Sobe os mesmos três endpoints com a biblioteca padrão do Python, para
a máquina em que não dá para instalar nada, e serve o banco de provas
na raiz. Não substitui o serviço oficial: não tem Swagger, não tem
OpenAPI e não deve ser usado na integração com os outros grupos. Não
contém nenhuma regra de negócio - chama executar_processo e
buscar_documento, como o FastAPI chama.

16.3. A ÚNICA MUDANÇA NO BACKEND: CORS

O navegador bloqueia uma página que chama um endereço de outra origem
sem os cabeçalhos de CORS, e uma página aberta do disco tem origem
"null". Por isso src/api.py passou a usar o CORSMiddleware do FastAPI,
e o servidor de fumaça responde aos mesmos cabeçalhos.

A liberação é permissiva - allow_origins=["*"]. É adequado a um serviço
de teste rodando em localhost, que é o caso deste projeto na
disciplina. Fica o registro explícito: antes de expor o serviço em
rede, a lista de origens precisa ser restringida. O aviso está no
código e no README.

Nenhum endpoint, nenhum contrato, nenhum schema e nenhuma resposta
mudou por causa do frontend.

16.4. TESTES

tests/test_frontend.py, com 9 testes:

- a página gerada é idêntica ao que o molde mais os exemplos produzem
  (falha quando alguém edita examples/ e esquece de regerar);
- o marcador do molde foi resolvido;
- cada exemplo embutido é idêntico ao arquivo de examples/;
- todo cenário de examples/ aparece na tela, e nenhum a mais;
- cada caso declara rótulo, descrição e código HTTP esperado;
- o caso inválido espera 400 e os demais esperam 201;
- a página cobre os três endpoints;
- a página não depende de build, framework nem CDN de biblioteca;
- a página declara idioma e viewport.

servidor: caso 1 respondeu 201 com o carimbo EMITIDO, a consulta dos
